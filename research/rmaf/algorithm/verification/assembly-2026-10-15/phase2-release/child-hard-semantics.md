**Semantic inferences from those facts.** The following are my mathematical reading of the cited definitions and proofs, rather than additional executed tests.

The original path convention agrees with the retained public target, which specifies directed child edges with the parent on the a–b path and child off it (`assembly/HARD-PARENT-REFINEMENT-TARGET-v1.md:6–24`). The retained baseline calls a rooted path a path in the underlying unrooted tree, defines Whidden's edges by tails on the path and heads outside it, and declines an added rho convention (`research/rmaf/sources/baseline/split-or-decompose-v2.txt:161–197,327–333`). `PathAt` retains endpoints explicitly (`geometry/Geometry.lean:12–23`), while `minimalVertices` starts at the selected LCA and retains intervening vertices (`RMAF.lean:124–133`). Therefore an ancestor edge entering an LCA below the original root is excluded from this pendant list. The remaining root component can include labels above that LCA. No new parent edge at the original root is present: the enumeration requires a nonempty child address (`Executable.lean:12–15`), and the actual edge relation requires valid original addresses (`core/CoreGraph.lean:23–25`). A leaf endpoint has no valid child to add to the list.

Sibling orientation is handled at both relevant points. `RootedIso` allows straight and swapped child correspondence (`RMAF.lean:28–33`), and `iso_hasCherry` transports both orientations (`Restriction.lean:32–47`). `ActualCherry` permits an actual target cherry with either a,b order, `pendantOriginal_swap` leaves the source list unchanged, and `actual_hard2_unordered_safety` swaps the singleton disjuncts when needed (`Safety.lean:126–152`). The exact final consumers take oriented `CherryAt`; a caller with an unordered cherry can select its actual orientation. The proof does not substitute a contracted cherry for the supplied original `CherryAt` (`core/CoreGraph.lean:20–21`).

The endpoint argument has no assumed optimum or coverage property. `checkedSourcePartition` constructs supports from the checked original minimal hulls, with connectedness and disjointness proved from the two checker hypotheses (`integration/SourceBridge.lean:243–267`). Its owner equality is equivalent to membership in one literal original F block (`SourceBridge.lean:271–293`). If neither cherry endpoint is singleton, connected supports contain the shared actual target parent, forcing the endpoints to have one owner (`Endpoint.lean:79–88`; `core/CoreGraph.lean:210–226`). `checked_singleton_is_literal` uses the exact partition count to turn a sole endpoint address into the literal block `[x]`, so the result does not depend on a set/list ambiguity (`Endpoint.lean:15–65`).

The source exclusion argument permits other selected labels above the cherry's source fork. `PrunedCherry.left/right` require only absence of a,b in the other original child; they do not require that child to have empty selected restriction (`PendantExclusion.lean:8–16,30–72`). Its inductive exclusion proof considers only original child edges leaving the two-label path (`PendantExclusion.lean:177–213`). In the common-block case, a different F block crossing a cut has a source hull containing the same original cut parent as the common a,b block, contradicting the checked source embeddings (`Refinement.lean:75–96`). Choosing any label of each nonempty F block then places its entire block in A, B, or the complement C (`Refinement.lean:113–130`). No F-refines-parent premise is supplied.

The graph claim is literal before suppression. Distinct cut heads form an antichain (`Components.lean:122–139`). The two descendant components and the complementary root component then follow from actual original residual walks (`Components.lean:231–249`; `OriginalGraph.lean:191–206`). Every valid original vertex belongs to one of them, and the three component roots are pairwise separated (`Components.lean:243–249,306–313`). Valid binary subtrees make A and B nonempty; an original endpoint supplies a leaf in C (`Components.lean:281–305`). The exact leaf-set equivalences use unique source labels (`Components.lean:250–280`), and each component contains a reachable original leaf (`Components.lean:314–323`). `literalThree_partition` separately proves nonempty blocks, exactly-one membership, and source-label support (`Safety.lean:32–78`). Both endpoints belong to C by `hard2_endpoints_in_root` (`Safety.lean:154–163`), with source endpoint membership derived from agreement (`Safety.lean:80–92`). Thus A, B, C are the proper original source parent labels required by the target.

The two named cuts can be fixed independently of F. `pendantOriginal` depends only on S,a,b (`Executable.lean:12–15`), is nodup (`Components.lean:32–34`), and a length-two list supplies its first and second entries (`Safety.lean:123–124`). `HardConsumer.hard2_clique_uniform` performs that selection before the `fun F q` (`HardConsumer.lean:49–58`). The named four-chain and diagonal calls likewise receive one fixed list equality and use `hard2_refinement_split` before splitting the endpoint alternatives (`HardConsumer.lean:60–99`). A universal four-chain/diagonal wrapper is not written there, but the named theorem parameters permit the same fixed-cut order without choosing cuts from F.

The exact connection to the final consumers has no additional hard-parent assumption. `leftParent`, `rightParent`, and `rootParent` unfold to the same A, B, C used by `literalThree` (`HardConsumer.lean:7–10`; `Executable.lean:22–25`). `hard2_refinement_split` passes only source Nodup, original agreement, actual target cherry, and exact source cut-list equality to named safety (`HardConsumer.lean:14–21`). The clique/four/diagonal cover proofs pass the resulting parent partition and derived refinement to their list-cover calls only in the refinement branch; the two endpoint branches remain the literal singleton disjuncts (`HardConsumer.lean:35–40,73–78,94–99`). The explicit budget premise is `F.length-1 ≤ q`, with no optimum predicate. `HardPaid` obtains each cover from those same calls and retains it as `Hard2Covered`, while separately deriving its mass expression (`HardPaid.lean:8–13,28–33,50–55,72–76`). The parent, rather than this child, reviews those separate list-cover and mass proofs.
